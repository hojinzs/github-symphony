# WORKFLOW.md Related Skills Section

## TL;DR

> **Summary**: When generating WORKFLOW.md via init, dynamically generate and include a `## Related Skills` section with the metadata (name + description + when to use) of the registered `.codex/skills`
> **Deliverables**: SkillTemplate type extension, Related Skills section generator, init wiring, tests
> **Effort**: Short
> **Parallel**: YES - 2 waves
> **Critical Path**: Task 1 (type extension) → Task 2 (generator + tests) → Task 3 (wiring)

## Context

### Original Request

When generating WORKFLOW.md via init, after registering `.codex/skills`, we also need to register Related Skills describing when and where the registered skills should be used.

### Interview Summary

- **Dynamic generation**: add `description` + `trigger` fields to the `SkillTemplate` type and auto-generate from `ALL_SKILL_TEMPLATES`
- **Level of detail**: name + description + when to use (3-part format)
- **Position**: right after Status Map, before Agent Instructions

### Metis Review (gaps addressed)

- **4 call sites**: `generateWorkflowMarkdown()` is called in 4 places, not 3 (including writeConfig) → treat `relatedSkills` as optional
- **Exclude gh-symphony**: exclude the meta skill just like reference-workflow.ts → include only the 5 agent-facing skills
- **Description duplication risk**: `SkillTemplate.description` and the description inside `renderSkillDocument()` are doubly maintained → acceptable within the current scope, can be refactored later
- **Empty array handling**: if `relatedSkills` is `undefined` or `[]`, do not output the section
- **buildPromptBody signature**: `relatedSkills` needs to be added as a second parameter
- **Test mock updates**: adding required fields to `SkillTemplate` requires updating existing test mocks
- **Korean language**: the existing WORKFLOW.md body is in Korean, so Related Skills should also be in Korean for consistency

## Work Objectives

### Core Objective

Have the WORKFLOW.md generated by `generateWorkflowMarkdown()` include the list of registered skills as a `## Related Skills` section, so that AI agents are aware of the available skills and when to use them.

### Deliverables

- Add `description`, `trigger` fields to the `SkillTemplate` type
- Add metadata to all 6 entries in `ALL_SKILL_TEMPLATES`
- Add a `relatedSkills` parameter to `generateWorkflowMarkdown()` and generate the section
- Pass skill metadata through all init paths
- Test coverage

### Definition of Done (verifiable conditions with commands)

- `pnpm --filter @gh-symphony/cli test` passes
- `pnpm typecheck` passes
- `pnpm lint` passes
- `pnpm build` passes
- Generated WORKFLOW.md contains the `## Related Skills` section (when relatedSkills is passed)
- Section not output when `relatedSkills` is not passed (backward compatible)

### Must Have

- `description: string` + `trigger: string` fields on the `SkillTemplate` type (required)
- `relatedSkills?: Array<{name: string; description: string; trigger: string}>` field on `GenerateWorkflowInput`
- The `## Related Skills` section positioned after `## Status Map` and before `## Agent Instructions`
- Each entry formatted as: `- **{name}**: {description} — *{trigger}*`
- The gh-symphony skill excluded from Related Skills (include only skills for agent work)
- No section output when `relatedSkills` is undefined/[]
- `parseWorkflowMarkdown()` + `renderPrompt(strict: true)` round-trip works correctly

### Must NOT Have (guardrails)

- No modifications to the individual skill generator files (commit.ts, push.ts, pull.ts, land.ts, gh-project.ts, gh-symphony.ts)
- No modifications to `renderSkillDocument()`
- No modifications to `reference-workflow.ts`
- No modifications to `tenant.ts`
- No modifications to the core package (parser.ts, lifecycle.ts, etc.)
- No adding skills-related fields to the front matter
